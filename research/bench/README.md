# 中文 + 代码标识符检索：SQLite FTS5 方案实测

> 用本机真实语料（`vault-src/`，36 个中文逆向笔记 md，594,017 字节 UTF-8）跑 10 个 FTS5 方案（必测 A/B/C/D + 可选 E，加 B2/C1/F/G/H 五个诊断与改进变体），回答 TECH-69「中文关键词（含代码标识符）能命中，返回相关度可接受」哪种实现能过。
>
> 环境：Windows / Python 3.12.10 / SQLite **3.49.1**（Python 内置模块与 `sqlite3` CLI 同版本，FTS5、trigram 均可用）。
> 产物：`bench.py`（一键复现）、`results.json`（全量数据）、`[A-H]_schema.sql`（每个方案的 DDL + 查询 SQL）。语料只读，未做任何修改。

---

## 0. 结论（先看这里）

**推荐方案：F —— 写入端 CJK bigram 预分词 + 代码标识符子 token 拆分，查询端做同样的变换并对 ASCII 标识符用前缀查询。**

- 只依赖 FTS5 自带的 `unicode61`，不依赖 trigram、不依赖自定义 tokenizer → **在 D1/Worker 上可确定性实现**（预分词在 JS 里做，SQL 只负责索引和 bm25）。
- 48 条正查询命中 47 条（hit@5 = **0.9792**），唯一漏的是 1 字中文「压」（1 字查询另作产品决策，见 §6.3）。
- 索引只 1.18× 语料（trigram 是 3.85×），总库 2.63×（trigram 4.92×）；写入时多一次 O(文本) 的变换（本机 594KB 约 60ms）。

**如果「返回相关度可接受」是硬指标，再加 G —— 段落级切片（≈600 字符/块）。**

- 文件级 bm25 的排序天花板很低：F 的 canonical@1 只有 0.542（4 字中文几乎从不把标题最相关的文件排第一，canonical@1 = 0）。
- G 把 canonical@1 提到 **0.708**、canonical@3 提到 **0.917**（4 字中文 0 → 0.70），命中率不变，查询耗时反而更低（0.12ms）；代价是总库 2.63× → 3.25×、行数 36 → 640。

**如果「标识符标点必须精确」也是硬指标，加 H —— F + 原文后验过滤。**

- tokenizer 会把 `_` `.` `-` 等分隔符抹平：`access_token` 会命中只写了 “access token” 的文档，`boot.img` 会命中 “boot img”。H 用原文对 top-50 候选做一次子串校验，precision@5 从 0.985 回到 **1.0**，代价是查询中位 0.14ms → 0.35ms（只对含分隔符的查询开启后验即可，见 §6.3）。

**明确否定的方案：**

| 方案 | 结论 | 硬证据 |
|---|---|---|
| A `unicode61` | ❌ 不可用。连续中文串被当成 **一个 token**，2 字词只能碰运气，4 字词命中率 0.30 | 见 A-1/A-2 micro check；§4.2 |
| B `trigram` | ❌ 不可用于中文。**任何 <3 字符的查询静默返回 0 结果，不报错**，2 字中文 0/5 命中 | B-1/B-2；§4.1 |
| B2 `trigram + LIKE` | ⚠️ 结果准（100%），但 100% 是 ground truth 定义的必然，代价是 content 全表扫、只剩 LIKE 时没有 bm25 排序 | §4.1、§4.6 |
| E `trigram + 标识符表` | ❌ 被 F 全面压制：同样漏 2 字中文，索引 4.15×、查询慢 1.6× | §3 |
| C1 `unigram+bigram` | ⚠️ 只在必须支持 1 字中文查询时才值得（索引 1.46×，查询 1 字可用） | §4.3 |

**Ground truth 的两个定义**（`bench.py` 里 `ground_truth()`；大小写不敏感，对整个文件文本）：

- `substr`：文件文本包含该查询串 → 该文件属于 GT。用于 1 字/2 字/4 字中文、标识符、hex。
- `all`：查询按空格切开，**每个 token 都出现**才属于 GT。用于「BLE 协议」「EBC 驱动」「心率 广播」这类多词查询——任务里说得很对，对带空格的中文查询用整串子串匹配太严格（语料写的是「BLE 协议与 .dat」而不是「BLE 协议」连写），所以必须有这个模式。

**canonical（「标准答案文件」）规则**：GT 中相对路径（去空格、小写）包含查询串的文件，多个取路径最短的；否则取包含该查询次数最多的 GT 文件。用来回答「最该出现的那个文件排第几」——这是「相关度可接受」最直接的代理指标（hit@k 只能说明「有一篇对的进了前 k」）。

**关于 GT 的两条诚实声明**（会直接影响读数）：

1. `HALL` 的 6 个 GT 文件里，`hall` 全部出现在 **`challenge`** 里，不是霍尔传感器。所以 token 方案（A/C/D/F/H）返回 0 是「token 语义正确、GT 定义严格」，不是 bug。trigram 因为子串语义返回了它。
2. `0x100B51CF` 在语料里实际是更长的 token **`0x100B51CF4`**（ASR 端点选择器那个表）。所以精确 token 方案漏、子串/前缀方案命中——这正好暴露了「标识符要不要前缀匹配」的工程问题，是 §4.4 的核心。

## 2. 方案定义

所有方案都用同一套表结构（FTS5 虚拟表 + `path UNINDEXED`），区别只在 **tokenizer** 和 **写入/查询时的文本变换**。完整 DDL 与查询 SQL 见同目录 `[A-H]_schema.sql`；变换函数见 `bench.py`。

| 方案 | tokenizer | 写入变换 | 查询端 | 说明 |
|---|---|---|---|---|
| **A** | `unicode61 remove_diacritics 2` | 无（原文） | 每个空白 token 加引号 AND | 基线，对照组 |
| **B** | `trigram` | 无（原文） | 同上 | SQLite 内置子串检索，要求 ≥3 字符 |
| **B2** | `trigram` | 无 | ≥3 字符走 MATCH，<3 字符走 `body LIKE '%x%'` | B 的诊断变体 |
| **C** | `unicode61` | 中文连续段 → 重叠 bigram（空格分隔），ASCII 原样 | 同样的变换；中文段用 **phrase**（`"心率 率广 广播"`），ASCII token 加引号，AND | 不依赖词典，Worker 可确定性实现 |
| **C1** | `unicode61` | C + 每个中文段再补 unigram（放在 bigram 之后，保持 phrase 邻接） | 同 C | 诊断：花 1.46× 索引买 1 字查询 |
| **D** | `unicode61` | C + 标识符子 token：`0x7000`→`7000`、`ABS_PRESSURE`→`ABS`/`PRESSURE`、`accountId`→`account`/`Id`（整词仍保留） | 同 C | 「代码标识符必须可搜」 |
| **F** | `unicode61` | 同 D | 同 C，但 ASCII 标识符 token 用**前缀**（`0x100b51cf*`） | 零索引成本换来长 token 变体命中 |
| **G** | `unicode61` | 同 F，但先按标题/段落切成 ≈600 字符块，一行一块 | 同 F，命中折叠回文件 | **补充实验**：验证 chunking 能否救排序 |
| **H** | `unicode61` | 同 F，额外存一列原文 `raw` | 同 F + 对 top-50 候选做原文子串校验 | 清掉分隔符折叠误报 |
| **E** | trigram 表 + unicode61 标识符表 | 无 | 两表分别查，RRF(k=60) 融合 | 任务里的可选混合方案 |

C/D/F 的核心不变式（写死在 `bench.py` 里，D1 上必须照抄）：

```
写入（Worker）：CJK 连续段 → 重叠 bigram，空格分隔；ASCII 原样（D/F 再拆子 token）
查询（Worker）：同一函数；CJK 段 → 一个 phrase（bigram 序列），ASCII token → 引号包住（F 前缀加 *），全部 AND
```

micro check 已经把这些行为钉死（`results.json.micro_checks`，**23/23 与预期一致**），可以直接当单测用：

| id | 行为 | 结果 |
|---|---|---|
| A-1/A-2 | unicode61 下 `压感等级与电机` 查 `压感` = 0，查整串 = 1 | 0 / 1 ✅ |
| B-1/B-2 | trigram 查 2 字 / 1 字 = **0 行，不报错** | 0 / 0 ✅ |
| B-3/B-4 | trigram 查 3 字 = 1；trigram 表 + LIKE 2 字 = 1 | 1 / 1 ✅ |
| C-0/C-6 | 文档写 `心率、广播`，查 `心率广播` = 0（标点断句）；查 `心率、广播` = 1 | 0 / 1 ✅ |
| C-1/C-2 | 文档写 `心率广播`，查 `心率广播` = 1；查 `心率 广播` 两篇都中 | 1 / 2 ✅ |

**怎么读这张表（很重要，否则会误判）：**

- `hit@1 = hit@3 = hit@5` 不是 bug：语料只有 36 个文件，GT 普遍有 4–24 个文件，而所有方案返回的行都**必然**满足（或强于）子串条件，所以只要返回了结果，第一条就在 GT 里。**这里 hit@k 实际测的是「有没有结果」（coverage）**，不是排序质量。
- 排序质量看 `canonical@1/@3`：F 0.542，G 0.708 —— 文件级 bm25 的天花板，以及 chunking 能救回来多少。
- `recall@5`（GT∩top5 / min(5,|GT|)）与 `GT覆盖@5`（GT∩top5 / |GT|）在 GT 大的查询上天然低，仅作参考。
- **B2 的 100% 是同义反复**：它的 GT 定义（子串）与实现（LIKE 子串）完全一致，所以必然全中、精确率 1.0；要读的是它的**代价**（content 全表扫、p95 0.86ms vs 0.20ms、只剩 LIKE 时没有 bm25 排序）。
- E 的 0.79 与 B 相同：trigram 的 2 字短板一条没修，还多花 2× 体积。

## 4. 逐条回答任务里点名要验证的问题

### 4.1 2 字中文在 trigram 下能不能用？——不能，而且是最坑的一种失败

```sql
-- 已实测（SQLite 3.49.1，micro check B-1）
SELECT count(*) FROM docs_b WHERE docs_b MATCH '"压感"';   -- 0，且不报错
```

- **静默返回 0**。不会报错、不会告警，业务方只会看到「搜不到」。
- 语料上后果：2 字中文查询 **0/5 命中**，中英混合查询 1/4 命中（`BLE 协议`、`EBC 驱动`、`心率 广播` 都因为其中一个词是 2 字而整体落空）。
- 兜底 `body LIKE '%压感%'` 确实能出正确结果（micro check B-4，B2 方案 hit@1 = 1.0），但那是 content 列全表扫：本机 594KB 语料 p95 从 0.20ms 涨到 0.86ms（4.3×），且**只剩 LIKE 条件时无法 `ORDER BY bm25`**（退化成按 path 排序）。语料大 100 倍就是 100 倍扫描时间，不能作为生产主路径。
- 3 字及以上 trigram 正常（`压感等`、`BLE`、`0x7000`、`LSPosed`、`CVE-2026-98260` 全中）。

### 4.2 默认 unicode61 为什么不行

`unicode61` 把**一整段连续中文当成一个 token**（A-1：文档 `压感等级与电机`，查 `压感` = 0，查整串 = 1）。中文写作习惯是没有空格的，所以：

- 2 字词能命中纯属运气：只有当原文里那两个字正好被标点/空格/换行围成独立一段时才成为 token。本语料上 5/5 命中，但那是笔记标题、表格单元格这类短串多的缘故，换语料就崩。
- 4 字词命中率直接掉到 **0.30**（`心率广播`、`数据出境`、`单导心电` 全漏）。
- 优点也真实：索引最小（索引 0.80× 语料、总库 1.86×），ASCII 标识符（含 `_` 分隔的 snake_case，因为 `_` 在 unicode61 里是分隔符）全中。
- 结论：**可以留作「标识符精确匹配」的辅助表（E 就是这么干的），但不能当主索引。**

### 4.3 bigram 方案：1 字 / 2 字 / 跨标点

- **2 字中文：5/5 命中**，canonical@1 = 0.6 —— 可用（C-1）。查询端把 `压感` 变成一个 bigram phrase，与索引里的 token 精确对齐。
- **1 字中文：基本不可用**（C-4：查 `压` = 0）。bigram 索引里没有 unigram；只有当该字在原文里被标点/空格单独隔开时才会以单 token 存在（本语料 `笔` 命中、`压` 不命中，均属运气）。要支持 1 字必须上 C1（索引 +40%，1.46×）。
- **跨标点词组：会断**（C-0）。文档写 `心率、广播`，查询 `心率广播` → phrase `"心率 率广 广播"` 需要三个 bigram 位置连续，`率广` 跨了标点不存在 → 0 结果。
  - 查询端保留标点可以救一半（C-6：查 `心率、广播` → 拆成 `"心率" AND "广播"` → 命中），**但文档侧被标点拆开、查询侧又没写标点时救不回来**。
  - 我们的选择：接受这个限制（用户搜 `心率广播` 时大多数笔记里也是连写的）；不建议写入时把标点统统替换成空格，那会把 `心率、广播` 和 `心率广播` 混为一谈，且让 phrase 语义更松。
  - 另有一个「假词切片」现象（C-3）：`率广` 这种非词 2 字也会作为 bigram 进索引并在查询时命中 `心率广播`。这对**正常查询无害**（用户不会搜 `率广`），但意味着**2 字中文查询的误报面比字面更大**，产品侧不要拿 2 字 CJK 做高亮定位。

### 4.4 标识符哪种方案能精确命中

先给结论：**「完整 token」大家都能中；差别在「长 token 的前缀/子词」和「标点分隔符」。**

| 查询 | GT | A | B | C | D | **F** | 说明 |
|---|---|---|---|---|---|---|---|
| `iAP2` `LSPosed` `nxnative` `Magisk` `protobuf` `CRC16` `Info.plist` `Mach-O` `2.6.55` `boot.img` `vbmeta` | 3–9 | ✅ | ✅ | ✅ | ✅ | ✅ | 完整 token，全部 top-1（`Info.plist`/`2.6.55` 在 B/E 是 top-2） |
| `ABS_PRESSURE` `access_token` `ActivityTaskManager` | 1–4 | ✅ | ✅ | ✅ | ✅ | ✅ | unicode61 的 `_` 是分隔符，phrase 匹配天然等效 |
| `0x7000` | 4 | ✅ | ✅ | ✅ | ✅ | ✅ | 整个 token |
| `7000` | 7 | ❌ | ✅ | ❌ | ✅ | ✅ | D 的 hex 子 token：`0x7000`→`7000` |
| `account` | 2 | ✅* | ✅ | ✅* | ✅ | ✅ | 语料里也有独立 `account`；D 另外让 `accountId` 命中 |
| `pressure` | 6 | ✅* | ✅ | ✅* | ✅ | ✅ | `ABS_PRESSURE` 经 `_` 拆分 |
| `0x100B51CF` | 1 | ❌ | ✅ | ❌ | ❌ | ✅ | 实际 token 是 `0x100B51CF4`，**只有前缀/子串能中** |
| `HALL` | 6 | ❌ | ✅ | ❌ | ❌ | ❌ | GT 全是 `challenge` 的子串；token 方案「语义正确地拒绝」 |

要点：

1. **精确 token ≠ 够用**。真实笔记里标识符经常带后缀/变体（`0x100B51CF4`、`accountIdV2`、`boot.img.bak`）。F 的 `token*` 前缀查询几乎零成本地解决了这一类（0x100B51CF → 命中，7000 canonical@1 也升到 1.0）。
2. **前缀只能用于 `[A-Za-z0-9_]+` 形态的 token**。`CVE-2026-*` 这种带 `-` 的不能当前缀词（FTS5 前缀查询要求 bareword），F 里对它们回退到普通 phrase，`CVE-2026-98260` 依然全中。
3. **分隔符折叠是真实误报源**：`access_token` 命中了只写 “access token” 的《Android 客户端静态逆向》，`boot.img` 命中了写 “boot img” 的文档。A/C/C1/D/F/G/E 都有这个毛病（P@5 0.985–0.989），只有 trigram（子串语义）和 H（原文后验）没有。**D1 上如果不处理，标识符搜索会掺入分隔符变体。**
4. trigram 在标识符上表现很好（子串语义天然覆盖前缀/后缀变体），但它在 2 字中文上的 0 命中是致命的——所以「用 trigram 做标识符、用 bigram 做中文」的混合 E 理论上有吸引力，实测被 F 全面压制（因为 F 的前缀查询已经拿到了 trigram 在标识符上的大部分收益，而 E 的中文短板一点没修）。

### 4.5 无结果查询是否误报

7 条不存在的查询（`电机`、`磁吸`、`量子纠缠`、`压感等级`、`SSL Pinning`、`handleHIDReport`、`zzqxnotexist`）× 10 个方案 = 70 次，**全部返回 0 条，零误报**。

- 中文不存在的词（`电机`）在 bigram 方案下要求 `电机` 这个 bigram 在索引里，不存在 → 0。bigram 的「假词切片」（§4.3）不会凭空造出 2 字短语，所以不会误报。
- 注意 `压感等级` 是**特意设计的「差一点但不存在」**：语料只有 `8192 压感`，没有 `压感等级`。所有方案都正确返回 0。
- `SSL Pinning`（`all` 模式）也不存在；`HALL` 的 GT 之所以是 6 个文件，是因为 `challenge` 的子串匹配（§1 声明 1），不是误报。

| 方案 | bm25 可用 | 备注 |

| A / B / C / C1 / D / F / G / H | ✅ 全部可用，分数是 float，`ORDER BY bm25(t)` 正常 | 表内只有一列被索引（body），无需列权重参数 |

## 5. 排名质量：为什么必须做 chunking

文件级索引下，bm25 的输入只有「这一篇里这个词出现几次 / 这篇多长」。真实笔记里一个词在长文档里出现 20 次、在标题里出现 1 次，标题那篇会被压到第 4–5 位。数据（`results.json` 的 `canonical_rank`）：

- `心率广播`：canonical 是一篇长文档，F 排第 **5**（5 个 GT 里最后一名）；`面部追踪`、`分区备份`、`协议逆向` 同样是第 3–4。
- `压感`：canonical 是一篇短文档，F 排第 2，第 1 是另一篇更大、提及更多的文档。
- 10 条 4 字中文查询，F 的 canonical@1 = **0.0**。

段落级 G 用同样的变换、同样的查询，只把「一行一文件」换成「一行 ≈600 字符块」，就能让 bm25 看到**局部词密度**：

| | F | G |
|---|---|---|
| canonical@1 | 0.542 | **0.708** |
| canonical@3 | 0.792 | **0.917** |
| 4 字中文 canonical@1 | 0.0 | **0.70** |
| 3 字中文 canonical@1 | 0.0 | **0.667** |
| hit@5 | 0.979 | 0.979（不变） |
| 查询中位 | 0.14ms | 0.12ms |
| 总库 | 2.63× | 3.25× |

补充手段（未单独测，成本很低，建议在 D1 上一起上）：

- FTS5 表加一列 `title`（或 `path` 的 token），`ORDER BY bm25(t, 5.0, 1.0)` 给标题权重——直接把「标题里带查询词」的文件顶上去。
- 或者 G + 标题加权组合。

## 6. 推荐方案与在 D1 / Worker 上实施时要注意的点

### 6.1 最终建议

```
写入：docs 表（path, raw, tokenizer_version）
      + fts 表  fts5(path UNINDEXED, body, tokenize='unicode61 remove_diacritics 2')
      body = bigram_ident_transform(raw)     ← 下面 §6.2 的算法
      （要排序质量：按标题/段落切 ~600 字符块，一行一块，path 重复）

查询：q = user query
      expr = bigram_ident_expr(q)            ← 同一个变换 + 前缀
      SELECT path, bm25(fts) FROM fts WHERE fts MATCH :expr ORDER BY bm25(fts) LIMIT 50
      → 折叠成文件、取前 5 →（可选）原文子串后验
```

一句话：**用 F（+ 标题权重），要排序就加 G 的切片；标识符标点敏感就加 H 的后验。** 不要用 trigram 做中文主索引，不要用 unicode61 裸跑。

### 6.2 写入端（Worker）注意点

1. **变换必须在 Worker 里做**，SQL 只收变换后的 body。D1 不支持自定义 tokenizer / 可加载扩展，所以「bigram」只能是写入时预分词——这正是 C/D/F 的设计前提。
2. 算法（与 `bench.py` 完全一致，直接移植）：
   - 扫字符串，切成「CJK 连续段」和「非 CJK 段」（CJK 范围 `\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff`）。
   - CJK 段长度 ≥2 → 输出所有重叠 bigram（`心率广播` → `心率 率广 广播`）；长度 =1 → 输出该字。
   - 非 CJK 段：D/F 先抽出 `[A-Za-z0-9][A-Za-z0-9_.\-/+:]*` 形态的「词」，每个词**先输出整词**，再输出子 token（`0x` 前缀去掉、`_ . - / + :` 切段、camelCase 切 `[A-Z]+(?![a-z])|[A-Z][a-z0-9]*|[a-z0-9]+`，长度 <2 的丢掉）。**整词必须先输出**，否则 phrase 邻接被破坏（`2.6.55`、`CVE-2026-98260` 就靠这个）。
3. **版本化**：docs 表加 `tokenizer_version`；变换算法一改，全量重算（或按 chunk 重算）+ 重建 FTS。把 §2 的 23 条 micro check 抄成 CI 单测，算法改动必须全绿。
4. **批量写**：每行 2–3 个绑定参数；D1 单条 SQL 最多 100 个绑定参数 → 一条 INSERT 最多 ~30–50 行，用 `db.batch()` 提交。单行 ≤1MB：本语料最大文件 38.6KB、变换后 ~55KB，安全；但**超长文档（>300KB）建议切片**，否则单行可能撞 1MB 限制。
5. **写入成本**：变换是 O(文本长度)，本机 Python 10ms/100KB；JS 更快但别在请求路径上对整库重建，按 chunk 增量更新（G 的额外好处）。

### 6.3 查询端（Worker）注意点

1. **必须用同一个变换函数**（共享模块，不要复制粘贴两份）。CJK 段 → 一个 phrase（`"心率 率广 广播"`）；ASCII token → 用双引号包住（内部 `"` 转义成 `""`）；**永远不要把用户输入直接拼进 MATCH**——FTS5 语法会吃掉 `-`、`*`、`OR` 等字符导致语义漂移或报错。
2. **前缀查询只给 `[A-Za-z0-9_]+`**（F 的规则）：`0x100b51cf*` ✅；`CVE-2026-*` ❌（用普通 phrase）。
3. **1 字中文另作产品决策**：bigram 索引里没有 unigram。三选一：① 产品层要求 ≥2 字（推荐，成本 0）；② 走标题/`LIKE` 兜底（贵）；③ 上 C1（索引 +40%）。**不要默认上 C1**。
4. **后验过滤按需开启**：只在查询 token 含 `_ . - / + :` 时才做（这类查询少），用 SQL `raw LIKE '%' || ? || '%'` 或 JS 子串判断，把「access_token = access token」这类误报清掉（H 的方案）。top-50 候选做校验，开销可控。
5. **高亮不要用 FTS5 的 `snippet()`**：F 的 content 是 bigram 变形文本（`"心率 率广 广播"`），snippet 出来是垃圾。用原文（docs.raw）+ JS 大小写不敏感子串定位来高亮。
6. **bm25 权重**：默认 `bm25(t)` 对 file-level 就够跑，但要排序质量就加标题列权重 `bm25(t, 5.0, 1.0)` 或上 G。

### 6.4 D1 上的验证清单（本地无法验证，上线前必须逐条跑）

D1 的 SQLite 版本与编译选项不保证和本机 3.49.1 一致；下面 3 条 SQL 就是最小探针：

```sql
SELECT sqlite_version();                                     -- 记录版本
CREATE VIRTUAL TABLE probe_fts USING fts5(x, tokenize='trigram');
INSERT INTO probe_fts(x) VALUES ('压感等级');
SELECT count(*) FROM probe_fts WHERE probe_fts MATCH '"压感"';   -- 预期 0（trigram <3 字静默 0）
SELECT count(*) FROM probe_fts WHERE x LIKE '%压感%';            -- 预期 1（LIKE 兜底是否存在）
```

- [ ] D1 是否支持 FTS5 虚表（官方文档/社区实践都说支持，但要亲测）。
- [ ] D1 是否带 **trigram** tokenizer（需要 SQLite ≥3.34；不保证）。**不带的把握很大也没关系**——推荐方案 F 只用 `unicode61`。
- [ ] `bm25()` 在 D1 查询里可用且返回 float。
- [ ] 单行 ≤1MB / 单条 SQL ≤100KB / 每查询 ≤100 绑定参数 / 查询 ≤30s（官方 limits）。我们的查询每句只用 1 个 MATCH 参数，不撞 100 参数限制；写入按 §6.2 批处理。
- [ ] **LIKE/GLOB pattern 官方限制 50 字节**——中文 UTF-8 3 字节/字，2 字查询 6 字节没问题，但别把整句塞进 LIKE；B2 的兜底在 D1 上要按这个上限设计。
- [ ] 用 `PRAGMA page_count * page_size` 量 D1 上的真实库体积（D1 没有 dbstat），和本文的 2.63× / 3.25× 对表。
- [ ] 并发/冷启动延迟实测（本文只测了单机相对量级）。
- [ ] 删除/更新路径：FTS5 的 DELETE 会写 tombstone，更新频繁时考虑 contentless 或按 chunk 删+插；D1 的单库容量（免费 500MB / 付费 10GB 级别，以官方 limits 页为准）要按 2.6–3.3× 原始文本预估。

## 8. 局限

1. **语料小（36 篇 / 594KB）**，且 single-corpus（全是中文逆向笔记）。结论方向（trigram 2 字不可用、unicode61 折叠、bigram 可用、chunking 救排序）是机制性的，换语料应成立；但具体命中率数字不要外推。
2. **GT 是子串定义**，会天然偏袒 trigram/子串方案；`HALL`/`0x100B51CF` 两例已经展示了定义对读数的影响。文件级 GT 也偏大，导致 hit@1/3/5 分不开，真正有区分力的是 canonical@1/3。
3. **canonical 是启发式规则**（路径包含查询串优先），不是人工标注；它对「标题就是答案」的查询合理，对宽泛查询（1 字）无意义。
4. **bm25 用默认参数**，没调 k1/b/列权重；把标题列加权后 canonical@1 应该还能再涨（未测）。
5. **计时是单机 Python 驱动 SQLite 的相对量级**，不是 D1 的线上延迟；写入成本也没含网络/事务开销。
6. 未测：并发、删除/更新后的 FTS 膨胀、snippet/highlight、段落级 + 标题权重的组合、Pinyin/同义词扩展。
